# Goo AI CLI — v2.0.0

**Codename:** Agent Mode
**Status:** Draft / Architecture Spec
**Depends on:** v1.x core (Groq integration, Tavily search, task management, GitHub tooling, AES-256-GCM/Argon2id encryption, three-layer memory system)

---

## 1. What this release is

Up to v1.x, goo is a terminal-first **chat assistant**: you ask it things, it answers, it searches, it remembers. It doesn't touch your filesystem and it doesn't run anything on your machine.

v2.0.0 adds a second mode: **agent mode**, invoked with `goo chat`. In this mode, goo can read and edit files across a project, propose and run terminal commands, and report back what it did — similar in spirit to Claude Code, Gemini CLI, or Warp's AI features, but built on goo's existing memory and provider layer rather than bolted on as a separate tool.

The two modes stay explicitly separate:

- `goo ask "<question>"` (or however the existing chat command is invoked) — **unchanged**. Pure Q&A, no filesystem or shell access. This is v1.x behavior, untouched.
- `goo chat` — **new**. Opens an agent session scoped to the current working directory (or a directory you `cd` into first, or hand it explicitly). Can read/write files, run shell commands, and reason across multiple files in a project.

This split matters for safety and for mental model: typing `goo ask` should never have side effects. Typing `goo chat` is an explicit declaration that you want goo to act, not just answer.

## 2. Core interaction model

### 2.1 Directory scoping

Two ways to start an agent session, both should work identically:

```bash
# Explicit target
goo chat --dir /home/king/Documents/your-rights "spin up a next.js app here"

# Implicit, via cwd
cd /home/king/Documents/your-rights
goo chat "spin up a next.js app here"
```

Logic:

1. On `goo chat` invocation, resolve the **project root**:
   - If `--dir` is passed, use it (validate it exists and is writable).
   - Otherwise use `os.Getwd()`.
2. Mark this as the **session root**. All file operations are sandboxed to this root and its subdirectories by default (see §5, Sandbox Boundaries) — goo should not silently wander up into `/home/king/Documents/` or beyond unless explicitly permitted in config.
3. If the directory is empty or doesn't look like a project yet (no `package.json`, `go.mod`, `.git`, etc.), goo treats this as a **bootstrap context** — it knows it may need to scaffold something (e.g. `create-next-app`) rather than assuming an existing codebase to edit.
4. If the directory has existing project files, goo runs a lightweight **project fingerprint** pass before doing anything else (see §4).

### 2.2 Session lifecycle

A `goo chat` invocation can be:

- **One-shot**: `goo chat "do X"` — runs the agent loop until the task is judged complete or blocked, then exits. Good for scripting, CI-adjacent use, or quick one-off asks.
- **Interactive**: `goo chat` with no prompt argument — drops into a REPL-style session in that directory. You can issue multiple instructions in sequence, and goo retains working memory of what it's done in *this session* (separate from the long-term three-layer memory system, which still applies for cross-session recall — see §7).

Both modes share the same underlying agent loop (§3). The only difference is whether the loop terminates after one task or waits for the next instruction.

## 3. The agent loop

This is the core logic. Every instruction given to `goo chat` runs through the same cycle:

```
┌─────────────┐
│   INSTRUCT   │  user gives a natural language instruction
└──────┬──────┘
       ▼
┌─────────────┐
│   PLAN       │  goo breaks instruction into discrete steps
└──────┬──────┘  (file reads, file writes, shell commands)
       ▼
┌─────────────┐
│   CLASSIFY   │  each step is tagged with a risk tier (§5)
└──────┬──────┘
       ▼
┌─────────────┐
│   GATE       │  risk tier determines whether confirmation
└──────┬──────┘  is required, per the user's configured policy
       ▼
┌─────────────┐
│   EXECUTE    │  step runs (file write / shell exec)
└──────┬──────┘
       ▼
┌─────────────┐
│   OBSERVE    │  capture result: stdout/stderr, exit code,
└──────┬──────┘  diff produced, errors
       ▼
┌─────────────┐
│   REPORT     │  render result to user via the UI layer (§6)
└──────┬──────┘
       ▼
   more steps?──yes──> back to PLAN (re-plan if needed)
       │
       no
       ▼
┌─────────────┐
│   SUMMARIZE  │  final summary of what changed
└─────────────┘
```

### 3.1 PLAN

Given an instruction like *"spin up a next.js app here"*, the planner needs to produce an ordered list of concrete steps, not just call an LLM once and hope. Suggested step schema:

```go
type Step struct {
    ID          string
    Kind        StepKind // FileRead | FileWrite | FileDelete | ShellExec | Search
    Description string   // human-readable, shown in UI
    Payload     any      // FileWritePayload, ShellExecPayload, etc.
    RiskTier    RiskTier // assigned in CLASSIFY, not PLAN
    DependsOn   []string // step IDs that must complete first
}
```

For the next.js bootstrap example, PLAN should produce something like:

```
1. ShellExec: npx create-next-app@latest . --typescript --tailwind --eslint --app
2. FileRead: package.json (verify scaffold succeeded)
3. ShellExec: npm install (if not auto-run by step 1)
4. Report: summary of created structure
```

For an editing instruction like *"add dark mode toggle to the navbar"*, PLAN should instead:

```
1. Search: locate navbar component (glob + grep, not full file dump)
2. FileRead: the navbar file(s) found
3. FileRead: any existing theme/context provider, if referenced
4. FileWrite: modified navbar with toggle
5. FileWrite: theme context, if one doesn't exist and is needed
6. Report: diff summary
```

This is the **full multi-file refactor awareness** requirement — PLAN should not be "read one file, write one file" in isolation. It needs a project-context pass first (§4) so it knows what other files might be affected by a change before it starts writing.

### 3.2 CLASSIFY

Every step gets tagged with a risk tier before it's eligible to run. This feeds directly into GATE. See §5 for the full tier definitions — this is the safety-critical part of the design and deserves its own section.

### 3.3 GATE

Reads the user's configured safety policy (set at install time, per your answer — overridable per-project or per-session) and the step's risk tier, and decides: auto-run, or block for confirmation.

### 3.4 EXECUTE

- `FileWrite` steps go through the diff-based patch system (§3.5), not naive overwrite.
- `ShellExec` steps run in a subprocess with captured stdout/stderr, a timeout, and the session root as cwd (unless the step explicitly needs elsewhere, which should itself be a flagged risk).
- All execution is logged to the session's working memory regardless of outcome, so a failure is visible to the next PLAN pass.

### 3.5 File writes are diff-based, not whole-file overwrites

Even though v2.0.0 targets full multi-file refactor awareness, the actual write mechanism should still be patch-based per-file — generate a diff, apply it, keep the old version recoverable. Full-file overwrite-and-pray is how agent tools destroy unrelated work in a file goo only partially understood.

Suggested approach, borrowing the shape of Claude Code's edit tool:

```go
type FileWritePayload struct {
    Path        string
    OldContent  string // exact substring expected to exist
    NewContent  string // replacement
    CreateIfMissing bool
}
```

Apply logic:
1. Read current file content.
2. Verify `OldContent` appears exactly once (refuse and re-plan if zero or multiple matches — this is what protects against goo confidently editing the wrong occurrence of something).
3. Apply replacement.
4. Write to a temp file, then atomic rename over the original (avoid partial writes on crash).
5. Store the pre-edit version in session state for `goo chat --undo` (see §8).

For **new files**, this collapses to `CreateIfMissing: true` with `OldContent` empty.

For **multi-file refactors** (the actual hard part): each individual file edit is still a discrete, independently-verified patch. What "multi-file awareness" buys you is in PLAN and §4 — goo deciding *which* files need touching and in what order — not in EXECUTE doing anything riskier per-file. This keeps the blast radius of any single mistake bounded to one file, even when the overall task spans ten.

### 3.6 OBSERVE and REPORT

Every step's result gets captured in a uniform shape so the UI layer (§6) can render it consistently:

```go
type StepResult struct {
    StepID    string
    Success   bool
    Output    string // stdout, or diff, depending on Kind
    ErrorMsg  string
    Duration  time.Duration
}
```

If a `ShellExec` fails (non-zero exit), goo should not silently move to the next step — it re-enters PLAN with the failure as new context, and either retries with a fix, asks the user how to proceed, or reports a blocker. This is what stops a failed `npm install` from cascading into five more broken steps.

## 4. Project fingerprinting (the "multi-file refactor awareness" foundation)

Before any non-trivial PLAN, goo needs a cheap pass to understand the project shape. This should be fast (no full-file reads of everything) and cached for the session.

Fingerprint pass collects:

- Project type signal: presence of `package.json`, `go.mod`, `Cargo.toml`, `requirements.txt`, `.git`, etc.
- For JS/TS projects: framework detection from `package.json` deps (Next.js, Express, vanilla, etc. — directly relevant given the range of stacks already in use across King's other projects).
- Directory structure, 2-3 levels deep, ignoring `node_modules`, `.git`, `dist`, `build`.
- For an editing instruction (not a bootstrap), a targeted search (glob/grep, not LLM-read-everything) to locate the files actually relevant to the instruction.

This fingerprint becomes part of the context passed to PLAN, so "add dark mode to the navbar" doesn't require goo to read every file in the project — it greps for `navbar`, `Nav`, `Header`, etc., reads only what's found, and plans from there.

Reuse this from existing memory/context-handling logic if goo's three-layer memory system already has primitives for this kind of structured context assembly — no need to build a second system if the first one's shape already fits.

## 5. Risk tiers and the safety model

Per your answer, the safety behavior should be **configured at install/setup time** rather than fixed in code, with three available policies. This means GATE doesn't hardcode behavior — it reads a policy object.

### 5.1 Risk tier definitions

Every step gets classified into one of these during CLASSIFY:

| Tier | Examples | Default treatment |
|---|---|---|
| **SAFE** | File reads, `git status`, `git diff`, `ls`, `npm list`, search/grep | Always auto-run, no policy applies — read-only ops are never gated |
| **LOW** | File writes within session root, `npm install` (no `-g`), `npm run build`, `git add` | Governed by configured policy |
| **MODERATE** | Running dev servers, `git commit`, package installs that modify lockfiles broadly, file deletes | Governed by configured policy, leans stricter |
| **HIGH** | Anything outside session root, `git push`, `rm -rf`, global installs (`npm install -g`), `sudo` anything, environment variable / secrets file access, network calls to non-allowlisted hosts | Always requires explicit confirmation regardless of policy — not overridable by the "auto-run" setting |

That HIGH-tier floor is important: even if a user's install-time setting is "auto-run safe/allowlisted, confirm risky," HIGH tier should not be auto-runnable by *any* policy setting. This is a hard ceiling, not a default. Letting the most permissive policy silently include `git push` or `rm -rf` would be the kind of decision that's hard to recover from. The three configurable policies all apply to LOW/MODERATE; HIGH always stops.

### 5.2 The three configurable policies

Set during `goo init` or `goo config set safety-policy <tier>`, with per-project override via a `.goorc` file in the project root.

**Policy A — Always confirm**
Every LOW and MODERATE step shows the proposed action and waits for explicit yes/no before running. Most conservative, slowest, best for unfamiliar codebases or production-adjacent work.

**Policy B — Allowlist auto-run**
A configurable allowlist of exact-match or pattern-match commands/operations that auto-run without confirmation (e.g. `npm install`, `npm run dev`, any `FileWrite` within session root). Anything not on the allowlist falls back to confirm. This needs a sane default allowlist shipped with goo, editable via `goo config edit-allowlist`.

**Policy C — Diff-and-approve**
For file writes specifically: instead of a yes/no prompt, show the diff inline and let a single keypress (`y`/`n`/`e` to edit before applying) resolve it. For shell commands under this policy, show the exact command string before running, same single-keypress flow. This is the "show command + diff, approve with one keypress" option — functionally a faster version of Policy A's confirmation, optimized for the actual review (diff/command) rather than a context-free yes/no.

These three are not mutually exclusive in spirit — Policy C is really Policy A with better UI, and Policy B can be combined with C (allowlisted things skip the diff-approve step too). Worth deciding at implementation time whether these are three separate code paths or one config struct with `requireConfirmation: bool`, `useAllowlist: bool`, and `approvalUI: 'prompt' | 'diff'` as independent toggles — the latter is probably cleaner and avoids combinatorial duplication if a user wants, say, allowlist + diff approval together.

### 5.3 Setup-time flow

```
$ goo init
...
? Choose a safety policy for agent mode (goo chat):
  > Always confirm before running commands or writing files
    Auto-run safe/allowlisted actions, confirm risky ones
    Show command/diff, approve with single keypress
    Let me configure this manually later (defaults to "Always confirm")

? [if Policy B] Use the default allowlist? (npm install, npm run *, git add, git status, file writes in project root)
  > Yes, use defaults
    No, let me customize
```

Stored in goo's existing config location (wherever the encrypted config/credentials currently live, given the AES-256-GCM setup — safety policy itself isn't sensitive, but should live alongside other settings for consistency).

## 6. UI layer — showing the user what's happening

This was explicitly called out as a requirement: file edits and terminal actions need visible, proper UI, not silent execution with a final text dump.

### 6.1 Live step rendering

As the agent loop runs, each step should render to the terminal in a structured, scannable way as it happens — not buffered until the end. Rough shape (exact terminal UI library choice — bubbletea, lipgloss, or similar, given this is Go — is an implementation detail, but the information hierarchy should be):

```
goo chat · /home/king/Documents/your-rights

→ Planning: "spin up a next.js app here"

  ✓ ShellExec  npx create-next-app@latest . --typescript --tailwind --app
    └─ done in 14.2s

  ✓ FileRead   package.json
    └─ verified scaffold

  ⏳ ShellExec  npm install
    └─ running...
```

For file writes, the diff should render inline, not just "file modified":

```
  ✎ FileWrite  components/Navbar.tsx
    ┌─────────────────────────────────
    │ - <nav className="flex">
    │ + <nav className="flex items-center justify-between">
    │ +   <ThemeToggle />
    └─────────────────────────────────
```

For shell commands awaiting confirmation (Policy A or B-fallback):

```
  ? ShellExec  git commit -m "add dark mode toggle"
    Run this command? [y/N/e to edit]
```

### 6.2 Final summary

At the end of a `goo chat` task (one-shot mode) or when the user asks for one in interactive mode:

```
Summary — 3m42s, 6 steps, 1 confirmation

  Created
    + app/layout.tsx
    + app/page.tsx
    + tailwind.config.ts

  Modified
    ~ components/Navbar.tsx  (+12 -2)
    ~ package.json           (+1 dependency)

  Ran
    npx create-next-app@latest .
    npm install

  Next.js app scaffolded and dev-ready. Run `npm run dev` to preview.
```

### 6.3 No-emoji rule

Carries over from Moxie and the rest of King's tooling — this should apply to all goo agent-mode output as well, including step labels, summaries, and any LLM-generated text in the report. Use plain status markers (✓/✗/⏳/✎/? as shown above are symbols, not emoji, and are fine) rather than emoji equivalents.

## 7. Interplay with the existing three-layer memory system

Agent mode shouldn't fork off a separate memory model — it should extend the existing one:

- **Session-local working memory** (new for v2.0.0): what steps have run *in this `goo chat` session*, their results, and any files touched. This is what lets PLAN re-plan intelligently after a failure, and what powers `goo chat --undo`.
- **Cross-session project memory**: if the existing three-layer system already supports per-project recall, agent-mode actions should write into it — e.g. "last time we worked in this directory, we scaffolded a Next.js app and added a Navbar with dark mode." This means a future `goo chat` session in the same directory starts with useful context instead of re-fingerprinting blind.
- **Long-term user memory**: stays as-is, governs things like the user's preferred stack, conventions, the no-emoji rule, etc., independent of any one project.

Where this needs design decisions rather than assumptions: whether agent-mode step history gets summarized down before being promoted from session-local to cross-session memory (likely yes, to avoid memory bloat from verbose tool I/O), and what the retention/eviction policy is for old project memories. Worth scoping explicitly rather than left implicit, since this is exactly the kind of thing CLAUDE.md flagged as a priority for the project already.

## 8. Undo / recoverability

Given agent mode can now modify files and run commands, a fast escape hatch matters:

- `goo chat --undo` — reverts the most recent file writes from session-local working memory (using the pre-edit snapshots stored in §3.5 step 5). Does **not** attempt to undo shell command side effects (can't un-run `npm install`), but should clearly report which step types it can and can't revert.
- Every session should have a lightweight session log (not necessarily committed to git, but written to disk, e.g. `.goo/sessions/<timestamp>.json`) so a session can be inspected or replayed even after the CLI exits, independent of cross-session memory.

## 9. Integration boundary: warp / claude code / gemini cli

Framing note for how this is positioned, not a technical dependency: goo isn't wrapping or shelling out to Claude Code or Gemini CLI — it's building the same *category* of agent capability (file edit + terminal exec + visible UI) natively, on goo's own provider layer (Groq, with whatever multi-provider abstraction already exists or needs adding). The comparison to those tools is about matching the interaction model users already expect from this category of tool, not about integrating with them directly.

If multi-provider support (e.g. routing some planning steps through a different model) is intended for a future release, that's a clean extension point given the agent loop is already provider-agnostic at the PLAN step boundary — but that's out of scope for v2.0.0 and worth keeping that way rather than scope-creeping into this release.

## 10. Scoped out of v2.0.0

Explicitly **not** in this release, to keep it shippable:

- Multi-provider routing for agent mode (Groq only, consistent with existing setup)
- Remote/SSH session support (`goo chat` targeting a directory on a different machine)
- Collaborative/multi-user agent sessions
- Plugin system for custom step types beyond FileRead/FileWrite/FileDelete/ShellExec/Search
- Background/daemon mode (agent running unattended on a schedule) — could be a v2.x direction but introduces a much bigger safety surface and deserves its own design pass

## 11. Open questions before implementation

- Does the existing three-layer memory system have a clean extension point for session-local working memory, or does this need a new fourth layer? (Leaning toward: extend, don't add a layer, to keep the model from sprawling — but worth confirming against the actual current memory code rather than assuming.)
- Terminal UI library choice (bubbletea + lipgloss is the common Go pairing for this kind of live-updating CLI UI, but worth confirming against whatever's already a dependency).
- Exact default allowlist contents for Policy B — needs a real pass against common workflows (Next.js, Go, Express, vanilla JS, given the existing project range) rather than a generic guess.
- Whether `.goorc` per-project config should also let a project override the *default* `--dir` sandbox boundary (e.g. explicitly permit writes one level up) — this is a real use case (monorepos) but expands the sandbox model and needs its own threat-model pass before being allowed.
