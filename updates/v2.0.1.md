## 0. How To Use This Document

This spec is written so it can be handed to an AI coding assistant in one pass and implemented end to end. It splits into three parts:

- **Part A** — MCP (Model Context Protocol) client support, so Goo can call tools exposed by any MCP server.
- **Part B** — Sub-agent orchestration, so Goo can decompose a task and run several agents in parallel under a lead agent.
- **Part C** — Where A and B meet: shared tool registry, shared safety policy, shared logging.

Each part defines motivation, architecture, Go types, config schema, CLI surface, and an end-to-end example. Both new packages are additive — nothing in v2.0.0 needs to be rewritten, only extended.

## 1. Assumed v2.0.0 Foundations

This document assumes the following already exist from the v2.0.0 agent-mode build. Where actual v2.0.0 type names differ, treat the names below as the target contract and rename at the call sites — the mapping is mechanical.

| Assumed component | Package | Role |
|---|---|---|
| `agent.Core` | `internal/agent` | The main agent loop: sends turns to the model, parses tool calls, executes them, feeds results back |
| `agent.SafetyPolicy` | `internal/agent` | Gates file writes and command execution behind `allow` / `deny` / `ask` rules |
| `tools.Tool` | `internal/tools` | Interface every callable tool implements: `Name()`, `Description()`, `Schema()`, `Execute(ctx, input)` |
| `tools.Registry` | `internal/tools` | Holds the set of tools available to a given agent session |
| `config.Config` | `internal/config` | Loaded from `~/.goo/config.yaml`; holds provider (Groq), model, and safety policy |

Import paths in this document assume a Go module named `goo` (i.e. `go.mod` declares `module goo`). If the real module path differs (e.g. `github.com/kingj/goo`), adjust the `goo/internal/...` imports below accordingly — everything else is unaffected.

This spec requires exactly one small addition to the existing v2.0.0 `agent.SafetyPolicy` type: a `Narrow(scope []string) SafetyPolicy` method, used only by the orchestrator (Section 22). Nothing else in `agent.Core`'s public surface needs to change.

## 2. Release Goals

### 2.1 In scope for v2.0.1
- MCP client: connect to MCP servers over stdio and Streamable HTTP, discover their tools, call them.
- Sub-agent orchestration: decompose a goal into tasks, run multiple agents in parallel, merge results.
- One safety-policy model that covers native tools, MCP tools, and every sub-agent — no second policy engine.

### 2.2 Out of scope (explicitly deferred, not started in this release)
- Goo acting as an MCP *server* (exposing itself to other hosts).
- Remote sessions, mobile control, scheduled/recurring runs.
- Mid-session provider switching (Groq remains the only provider touched by this spec).
- MCP resources and prompts primitives — this spec implements tools only, which is the primitive Goo actually needs today.

### 2.3 Release Philosophy
v2.0.1 ships as one build. MCP support without orchestration is half a release; orchestration without MCP-aware sub-agents is the other half. Both land together, gated by the checklist in Section 33 — consistent with shipping complete releases rather than staged rollouts.

# PART A — MCP INTEGRATION

## 3. Why MCP

Goo's tool surface today (v2.0.0) is whatever is compiled into the binary: file edit, terminal exec, and whatever else shipped with agent mode. MCP turns that into an open surface — any MCP server (filesystem, GitHub, databases, internal company tools) becomes a Goo tool without a maintainer writing bespoke integration code for each one. This is the same mechanism that lets terminal coding agents reach things like Google Drive, issue trackers, and chat tools without hardcoding any of them — and it is the highest-leverage single feature to add to an agent CLI.

## 4. Current MCP Transport Landscape (for implementers)

The MCP specification currently supports two transports:

- **stdio** — the client spawns the server as a subprocess and speaks newline-delimited JSON-RPC 2.0 over stdin/stdout. Local-only, single-client, simplest to implement, and the most widely supported transport across existing MCP servers.
- **Streamable HTTP** — the server exposes a single HTTP endpoint that accepts POST and GET, optionally upgrading to Server-Sent Events for streaming responses. Used for remote or shared servers, and supports session IDs and standard HTTP auth.

A third, older transport (plain two-endpoint SSE) has been deprecated in favor of Streamable HTTP. Goo v2.0.1 implements stdio and Streamable HTTP only; it does not implement legacy SSE.

## 6. Core Go Types

```go
// internal/mcp/types.go
package mcp

import (
	"context"
	"encoding/json"
)

type TransportKind string

const (
	TransportStdio TransportKind = "stdio"
	TransportHTTP  TransportKind = "http"
)

// ServerConfig describes one configured MCP server.
type ServerConfig struct {
	Name      string        `yaml:"name"`
	Transport TransportKind `yaml:"transport"`
	Enabled   bool          `yaml:"enabled"`

	// stdio-only
	Command string            `yaml:"command,omitempty"`
	Args    []string          `yaml:"args,omitempty"`
	Env     map[string]string `yaml:"env,omitempty"`

	// http-only
	URL     string            `yaml:"url,omitempty"`
	Headers map[string]string `yaml:"headers,omitempty"`

	// optional per-server override of the global safety policy (Section 11)
	SafetyPolicy string `yaml:"safety_policy,omitempty"`
}

// ToolDescriptor is what a server advertises via tools/list.
type ToolDescriptor struct {
	ServerName  string
	Name        string
	Description string
	InputSchema json.RawMessage
}

// ToolResult is the normalized output of a tools/call.
type ToolResult struct {
	Content []ContentBlock
	IsError bool
}

type ContentBlock struct {
	Type string // "text", "image", "resource"
	Text string
	Data string // base64, for non-text blocks
}

// Transport abstracts stdio vs Streamable HTTP behind one interface.
type Transport interface {
	Connect(ctx context.Context) error
	Request(ctx context.Context, method string, params any) (json.RawMessage, error)
	Notify(ctx context.Context, method string, params any) error
	Close() error
}
```

```go
// internal/mcp/client.go
package mcp

import (
	"context"
	"encoding/json"
	"fmt"
	"sync"
)

type Client struct {
	cfg       ServerConfig
	transport Transport
	mu        sync.RWMutex
	tools     []ToolDescriptor
	connected bool
}

func NewClient(cfg ServerConfig) (*Client, error) {
	var t Transport
	switch cfg.Transport {
	case TransportStdio:
		t = NewStdioTransport(cfg.Command, cfg.Args, cfg.Env)
	case TransportHTTP:
		t = NewHTTPTransport(cfg.URL, cfg.Headers)
	default:
		return nil, fmt.Errorf("mcp: unknown transport %q for server %q", cfg.Transport, cfg.Name)
	}
	return &Client{cfg: cfg, transport: t}, nil
}

func (c *Client) Connect(ctx context.Context) error {
	if err := c.transport.Connect(ctx); err != nil {
		return fmt.Errorf("mcp: connect %q: %w", c.cfg.Name, err)
	}
	if _, err := c.transport.Request(ctx, "initialize", initializeParams()); err != nil {
		return fmt.Errorf("mcp: initialize %q: %w", c.cfg.Name, err)
	}
	if err := c.transport.Notify(ctx, "notifications/initialized", nil); err != nil {
		return fmt.Errorf("mcp: initialized notify %q: %w", c.cfg.Name, err)
	}
	c.mu.Lock()
	c.connected = true
	c.mu.Unlock()
	return nil
}

func (c *Client) ListTools(ctx context.Context) ([]ToolDescriptor, error) {
	raw, err := c.transport.Request(ctx, "tools/list", nil)
	if err != nil {
		return nil, fmt.Errorf("mcp: tools/list %q: %w", c.cfg.Name, err)
	}
	var resp struct {
		Tools []struct {
			Name        string          `json:"name"`
			Description string          `json:"description"`
			InputSchema json.RawMessage `json:"inputSchema"`
		} `json:"tools"`
	}
	if err := json.Unmarshal(raw, &resp); err != nil {
		return nil, fmt.Errorf("mcp: decode tools/list %q: %w", c.cfg.Name, err)
	}
	out := make([]ToolDescriptor, 0, len(resp.Tools))
	for _, t := range resp.Tools {
		out = append(out, ToolDescriptor{
			ServerName:  c.cfg.Name,
			Name:        t.Name,
			Description: t.Description,
			InputSchema: t.InputSchema,
		})
	}
	c.mu.Lock()
	c.tools = out
	c.mu.Unlock()
	return out, nil
}

func (c *Client) CallTool(ctx context.Context, name string, args json.RawMessage) (ToolResult, error) {
	raw, err := c.transport.Request(ctx, "tools/call", map[string]any{
		"name":      name,
		"arguments": json.RawMessage(args),
	})
	if err != nil {
		return ToolResult{}, fmt.Errorf("mcp: tools/call %s@%s: %w", name, c.cfg.Name, err)
	}
	var result ToolResult
	if err := json.Unmarshal(raw, &result); err != nil {
		return ToolResult{}, fmt.Errorf("mcp: decode tools/call result: %w", err)
	}
	return result, nil
}

func (c *Client) Close() error { return c.transport.Close() }
```

## 7. Manager — Multi-Server Registry

```go
// internal/mcp/manager.go
package mcp

import (
	"context"
	"fmt"
	"log/slog"
)

type Manager struct {
	clients map[string]*Client
	logger  *slog.Logger
}

func NewManager(logger *slog.Logger) *Manager {
	return &Manager{clients: make(map[string]*Client), logger: logger}
}

func (m *Manager) LoadFromConfig(ctx context.Context, servers []ServerConfig) error {
	for _, sc := range servers {
		if !sc.Enabled {
			continue
		}
		client, err := NewClient(sc)
		if err != nil {
			return err
		}
		if err := client.Connect(ctx); err != nil {
			m.logger.Warn("mcp server failed to connect, skipping", "server", sc.Name, "error", err)
			continue
		}
		if _, err := client.ListTools(ctx); err != nil {
			m.logger.Warn("mcp server connected but tools/list failed", "server", sc.Name, "error", err)
			continue
		}
		m.clients[sc.Name] = client
	}
	return nil
}

func (m *Manager) Client(name string) (*Client, bool) {
	c, ok := m.clients[name]
	return c, ok
}

func (m *Manager) Reconnect(ctx context.Context, name string) error {
	c, ok := m.clients[name]
	if !ok {
		return fmt.Errorf("mcp: no server named %q", name)
	}
	_ = c.Close()
	return c.Connect(ctx)
}

func (m *Manager) CloseAll() {
	for _, c := range m.clients {
		_ = c.Close()
	}
}
```

## 8. Adapting MCP Tools Into `tools.Registry`

```go
// internal/mcp/adapter.go
package mcp

import (
	"context"
	"encoding/json"
	"fmt"

	"goo/internal/agent"
	"goo/internal/tools"
)

type toolAdapter struct {
	client *Client
	desc   ToolDescriptor
	policy agent.SafetyPolicy
}

func (a *toolAdapter) Name() string {
	return fmt.Sprintf("%s:%s", a.desc.ServerName, a.desc.Name)
}

func (a *toolAdapter) Description() string { return a.desc.Description }

func (a *toolAdapter) Schema() tools.ToolSchema {
	return tools.ToolSchema{Raw: a.desc.InputSchema}
}

func (a *toolAdapter) Execute(ctx context.Context, input json.RawMessage) (tools.ToolResult, error) {
	decision := a.policy.Check(agent.Action{
		Kind:   agent.ActionMCPCall,
		Target: a.Name(),
		Detail: string(input),
	})
	if decision == agent.Deny {
		return tools.ToolResult{}, fmt.Errorf("blocked by safety policy: %s", a.Name())
	}
	if decision == agent.Ask {
		// Reuse whatever confirmation UI v2.0.0 already shows for ask-policy
		// file edits — same prompt/confirm/deny flow, different payload.
		if !agent.Confirm(ctx, a.Name(), string(input)) {
			return tools.ToolResult{}, fmt.Errorf("declined by user: %s", a.Name())
		}
	}
	res, err := a.client.CallTool(ctx, a.desc.Name, input)
	if err != nil {
		return tools.ToolResult{}, err
	}
	return tools.ToolResult{Content: mcpContentToNative(res.Content), IsError: res.IsError}, nil
}

func mcpContentToNative(blocks []ContentBlock) []tools.ContentBlock {
	out := make([]tools.ContentBlock, len(blocks))
	for i, b := range blocks {
		out[i] = tools.ContentBlock{Type: b.Type, Text: b.Text, Data: b.Data}
	}
	return out
}

// BuildToolList adapts every discovered MCP tool from every named,
// connected server into the native tools.Tool interface, ready to merge
// into tools.Registry alongside file/exec tools.
func BuildToolList(mgr *Manager, servers []string, policy agent.SafetyPolicy) []tools.Tool {
	var out []tools.Tool
	for _, name := range servers {
		client, ok := mgr.Client(name)
		if !ok {
			continue
		}
		for _, d := range client.tools {
			out = append(out, &toolAdapter{client: client, desc: d, policy: policy})
		}
	}
	return out
}
```

## 11. Safety Policy Integration

MCP tool calls are not a special case — they pass through the same `agent.SafetyPolicy.Check()` gate that file edits and terminal commands already use in v2.0.0.

| Policy value | Native tool behavior (v2.0.0) | MCP tool behavior (v2.0.1) |
|---|---|---|
| `allow` | Executes immediately | Executes immediately |
| `ask` | Prompts with a diff/command preview | Prompts with server name, tool name, and arguments |
| `deny` | Blocked, logged | Blocked, logged |

Per-server overrides are supported so a trusted local server can be `allow` while a remote server defaults to `ask`:

```yaml
mcp_servers:
  - name: filesystem
    transport: stdio
    command: npx
    args: ["-y", "@modelcontextprotocol/server-filesystem", "."]
    enabled: true
    safety_policy: allow   # overrides the global default for this server only
```

## 12. Error Handling & Reconnection

- Connection failures at startup: log a warning, skip the server, continue loading the rest — a broken server should never block Goo from starting.
- Failures mid-session: on the next tool call to that server, attempt one reconnect before surfacing the error to the model.
- `goo mcp test <name>` never touches the agent loop — it's a standalone connect / list-tools / close cycle for debugging.
- Stdio subprocess crashes are detected via process exit code; the client marks itself disconnected and the next call triggers reconnect.

## 13. End-to-End Example Flow

1. User runs `goo` in a project directory with `filesystem` and `github` MCP servers enabled.
2. On startup, `mcp.Manager.LoadFromConfig` connects both, lists their tools, and `BuildToolList` merges them into `tools.Registry` alongside native `file_edit` and `exec` tools.
3. User says: "check if there's an open GitHub issue about the login bug, and if so read the related file."
4. The model emits a tool call for `github:list_issues`. `toolAdapter.Execute` checks the safety policy (`ask`), the user confirms, the call goes out over Streamable HTTP.
5. The model reads the result and emits a follow-up tool call — either the native `file_read` tool or `filesystem:read_file`, whichever the model selects.
6. The response is composed and shown to the user.

# PART B — SUB-AGENT ORCHESTRATION

## 15. Motivation

A single `agent.Core` loop is bottlenecked by the size of one context window and by doing everything serially. A large refactor — say, "add `context.Context` to every function in the `http` package" — is really N independent, similarly-shaped tasks, one per file or per cluster of files. Sub-agent orchestration lets Goo split that work across several agent loops running concurrently, each with a narrow, isolated context, coordinated by a lead agent.

## 16. Core Concepts

- **Lead agent** — the `agent.Core` instance the user is actually talking to. It plans the decomposition and merges results. It does not itself perform the file edits for delegated tasks.
- **Sub-agent** — a fresh `agent.Core` instance, scoped to one `Task`, with its own context window seeded only with what that task needs.
- **Task** — a unit of work: description, file scope (glob patterns it's allowed to touch), and a parent reference back to the lead session.
- **Orchestrator** — owns the worker pool, task queue, and result aggregation; the only new "brain" component in Part B.

## 17. Architecture Overview

```
                    +----------------------+
                    |      Lead Agent       |
                    |     (agent.Core)      |
                    +----------+-----------+
                               |
                     goal: "refactor http package"
                               v
                    +----------------------+
                    |     Orchestrator      |
                    |   - Decompose()       |
                    |   - RunParallel()     |
                    |   - Merge()           |
                    +----------+-----------+
                               |
             +--------+--------+--------+--------+
             v        v        v        v
        +--------+ +--------+ +--------+ +--------+
        |SubAgent| |SubAgent| |SubAgent| |SubAgent|
        | task 1 | | task 2 | | task 3 | | task 4 |
        +---+----+ +---+----+ +---+----+ +---+----+
            |           |          |          |
            v           v          v          v
       file scope   file scope  file scope  file scope
       (disjoint)   (disjoint)  (disjoint)  (disjoint)
                               |
                    +----------v-----------+
                    |  TaskResult[] merged  |
                    |  back into one diff   |
                    +-----------------------+
```

## 18. Concurrency Model

Sub-agents run as goroutines bounded by a semaphore sized from `orchestration.max_parallel_agents`. A failed sub-agent does not cancel its siblings — see Section 21.

```go
// internal/orchestrator/orchestrator.go
package orchestrator

import (
	"context"
	"sync"

	"goo/internal/agent"
	"goo/internal/tools"
)

type Task struct {
	ID          string
	Description string
	Scope       []string // glob patterns this task may touch
	ParentID    string
}

type TaskResult struct {
	TaskID string
	Diffs  []agent.FileDiff
	Log    []agent.Turn
	Err    error
}

// ToolProvider supplies the merged native+MCP tool set (from Part A),
// filtered down to what a given scope is allowed to see.
type ToolProvider interface {
	ToolsForScope(scope []string) []tools.Tool
}

type Orchestrator struct {
	lead      *agent.Core
	maxAgents int
	policy    agent.SafetyPolicy
	toolsFor  ToolProvider
}

func New(lead *agent.Core, maxAgents int, policy agent.SafetyPolicy, tp ToolProvider) *Orchestrator {
	return &Orchestrator{lead: lead, maxAgents: maxAgents, policy: policy, toolsFor: tp}
}

func (o *Orchestrator) RunParallel(ctx context.Context, tasks []Task) []TaskResult {
	results := make([]TaskResult, len(tasks))
	sem := make(chan struct{}, o.maxAgents)
	var wg sync.WaitGroup

	for i, t := range tasks {
		wg.Add(1)
		sem <- struct{}{}
		go func(i int, t Task) {
			defer wg.Done()
			defer func() { <-sem }()

			sub := agent.NewCore(agent.CoreConfig{
				Tools:  o.toolsFor.ToolsForScope(t.Scope),
				Policy: o.policy.Narrow(t.Scope), // sub-agent can never exceed the lead's grant
			})
			results[i] = runTask(ctx, sub, t)
		}(i, t)
	}
	wg.Wait()
	return results
}

func runTask(ctx context.Context, sub *agent.Core, t Task) TaskResult {
	diffs, log, err := sub.RunToCompletion(ctx, t.Description)
	return TaskResult{TaskID: t.ID, Diffs: diffs, Log: log, Err: err}
}
```

## 19. Task Decomposition Strategies

**Auto-decompose** (default): the lead agent makes one model call whose only job is to produce a task list — not to do the work — given the user's goal and a directory listing. The model returns a structured task list, parsed into `[]Task`. File scopes are assigned so no two tasks overlap; overlapping requests are merged into one task rather than split.

**Manual**: the user supplies the task list directly.

```yaml
# tasks.yaml
tasks:
  - id: t1
    description: "Add context.Context as the first parameter to every exported function in internal/http/client.go"
    scope: ["internal/http/client.go"]
  - id: t2
    description: "Same for internal/http/server.go"
    scope: ["internal/http/server.go"]
```

```bash
goo agent run --tasks tasks.yaml --parallel
```

## 20. Context Isolation

Each sub-agent's context window contains only:

1. The task description.
2. The contents of files matching its `Scope` — not the whole repo.
3. Any shared project-level memory file (the Goo equivalent of a `CLAUDE.md`, if v2.0.0 already has one — reuse it verbatim here).

Sub-agents never see each other's conversation history or diffs mid-run. This keeps each context window small — cheaper, faster, less prone to drift — and makes tasks safely parallelizable: two sub-agents can't develop inconsistent assumptions about a file neither of them owns, because neither can see it.

## 21. Result Aggregation & Conflict Resolution

- Because file scopes are disjoint by construction (Section 19), the common case has zero conflicts: `Merge()` just concatenates diffs.
- If a task fails (`TaskResult.Err != nil`), its diffs are discarded and its scope is reported back as "not completed" — sibling tasks are unaffected and keep running.
- If a manual `tasks.yaml` specifies overlapping scopes (user error), the orchestrator refuses to start and reports the overlapping file(s) before any agent runs.

```go
type MergeReport struct {
	Applied []string // file paths successfully written
	Failed  []string // task IDs that errored
}

func Merge(results []TaskResult, apply func(agent.FileDiff) error) MergeReport {
	var report MergeReport
	for _, r := range results {
		if r.Err != nil {
			report.Failed = append(report.Failed, r.TaskID)
			continue
		}
		for _, d := range r.Diffs {
			if err := apply(d); err != nil {
				report.Failed = append(report.Failed, r.TaskID)
				continue
			}
			report.Applied = append(report.Applied, d.Path)
		}
	}
	return report
}
```

## 22. Safety Policy Inheritance

A sub-agent's `SafetyPolicy` is always `lead.Policy.Narrow(task.Scope)` — the intersection of the lead session's policy and the task's file scope. A sub-agent can never:

- touch a file outside its assigned scope, even if the lead session's policy is `allow`
- escalate `ask` to `allow` on its own
- run a terminal command unless the lead session's policy explicitly permits terminal execution for that scope

This is the one addition to `agent.SafetyPolicy` flagged in Section 1: a `Narrow(scope []string) SafetyPolicy` method that returns a copy of the policy restricted to the given file globs. `ask`-level prompts from sub-agents are queued and surfaced through the lead session's UI, tagged with the originating task ID, rather than opening several concurrent prompts at once.

## 25. End-to-End Example Flow

1. `goo agent run "add context.Context everywhere in internal/http" --parallel`.
2. The lead agent calls the model once with the decomposition prompt and gets back four tasks, one per file in `internal/http`.
3. The orchestrator starts four sub-agents, bounded by `max_parallel_agents: 4`, so all four run at once.
4. Each sub-agent edits its one file, using the same native + MCP tool set as the lead session, gated by its narrowed policy.
5. `goo agent status` shows live progress while it runs.
6. On completion, `Merge()` applies all successful diffs as one commit-ready changeset; task t3's failure (say, a compile error it couldn't resolve) is reported separately with its partial log for the user to finish by hand.

# PART C — CROSS-CUTTING CONCERNS

## 27. Sub-Agents Calling MCP Tools

Sub-agents receive tools from the same `ToolProvider` the lead agent uses (Section 18), backed by the merged native + MCP tool list from Part A. An MCP filesystem server, for instance, is just as available to a sub-agent as the native `file_edit` tool, filtered the same way by `Scope`.

## 28. One Permission Model

| Action | Gate | Enforced by |
|---|---|---|
| Native file edit / exec (lead session) | `agent.SafetyPolicy.Check` | v2.0.0, unchanged |
| MCP tool call (lead session) | `agent.SafetyPolicy.Check` | Part A, Section 11 |
| Native file edit / exec (sub-agent) | `lead.Policy.Narrow(scope).Check` | Part B, Section 22 |
| MCP tool call (sub-agent) | `lead.Policy.Narrow(scope).Check` | Part A + Part B combined |

There is exactly one policy engine in the codebase; MCP and orchestration both consume it rather than each growing their own.

## 29. Logging & Observability

Structured logs, one file per agent, under `~/.goo/logs/<session-id>/`:

```
~/.goo/logs/2026-07-04T18-30-00/
    lead.log
    t1.log
    t2.log
    t3.log
    t4.log
    mcp-filesystem.log
    mcp-github.log
```

Each line is a JSON object, e.g. `{"ts": ..., "agent": "t2", "level": "info", "msg": "tool_call", "tool": "filesystem:read_file"}`. `goo agent status` and `goo mcp list` both read from these logs rather than keeping separate in-memory state, so status survives a crash.

## 31. Migration Guide (v2.0.0 to v2.0.1)

1. Add `internal/mcp` and `internal/orchestrator` as new packages. No existing package is deleted or renamed.
2. Extend `config.Config` with `MCPServers []mcp.ServerConfig` and `Orchestration OrchestrationConfig` fields — both optional and zero-value-safe, so existing v2.0.0 config files keep working unmodified.
3. Extend `tools.Registry`'s constructor to accept an additional `[]tools.Tool` slice (the MCP-adapted tools from `mcp.BuildToolList`) — additive, not a breaking signature change if the existing constructor is kept as a thin wrapper that passes `nil`.
4. Add the `goo mcp *` and `goo agent *` subcommand trees to the CLI dispatcher.
5. Add one method, `Narrow(scope []string) SafetyPolicy`, to the existing `agent.SafetyPolicy` type. No other change to `agent.Core`'s public API is required — both new features are built entirely on things it already knows how to consume: tools and policies.

This is additive-only. A user who never configures an MCP server or runs `goo agent run --parallel` will not notice v2.0.1 changed anything.

## 32. Testing Plan

- **Manual QA**: run both features together against a real multi-file refactor task in a throwaway repo before tagging the release.
